## 1. 内链在 DevBox 里到底解决什么

通用 SEO 教程列的内链七大作用(传权重 / 助抓取 / 消孤岛 / 强主题 / 提停留 / 顶重点页 / 建集群),对本站的具体映射:

| 通用作用 | 在 DevBox 的具体兑现 |
|---------|--------------------|
| 传递页面权重 | 首页(权重最高)→ 工具支柱页 → 内容页;内容页反链回支柱页,把权重回灌到**交易型落点** |
| 帮助蜘蛛发现新页面 | 新增一篇 `examples`/`troubleshooting`,只要挂进集群互链,就有入链被抓取,不必等 sitemap |
| 减少孤岛页面 | 每篇内容页至少有:面包屑入链 + 支柱页"深入了解"入链 + 兄弟页互链,**天然无孤儿** |
| 增强主题相关性 | 同簇内容(cron 的是什么/教程/示例/排查)密集互链,向搜索引擎强化「这一簇都在讲 cron」 |
| 提升用户停留时间 | 教程读完给"继续了解"、支柱页给"深入了解",顺路多看一页 |
| 帮助重点页面获得排名 | 内链锚文本集中喂给**支柱页主词**(如「Cron 表达式生成器」),把交易页顶上去 |
| 构建主题集群 | 这正是本站结构的核心:URL 筒仓(`/cron/*`)+ 内链筒仓 = 一个高内聚的 topic cluster |

> **一句话**:本站不是"文章站靠内链串联",而是"**每个工具是一个闭合筒仓**",内链的首要任务是让权重在簇内聚合、并回灌到交易型的支柱页。

## 2. 内链布局蓝图(每页应含哪些内链)

通用布局法(每篇重要页含:1 条→核心专题页 / 2–5 条→相关内容 / 1 条→转化页 / 1 条面包屑 / 1 个相关推荐模块)在本站的落法,**按页型拆解**:

### 2.1 内容页(`/cron/guide` 等信息型)

| 内链槽位 | 数量 | 指向 | 现状 |
|---------|------|------|------|
| 面包屑 | 1 | 首页 › 工具支柱页 | ✅ `Breadcrumb.astro` |
| 顶部工具 CTA(=转化页) | 1 | 本簇支柱页 `/{tool}` | ✅ `ArticleLayout` 顶部紫色卡片 |
| 正文内语义内链 | 2–5 | 兄弟内容页 / 支柱页,**按上下文语义** | ⚠️ 手写(见 §4) |
| "继续了解"推荐模块 | 全部兄弟页 | 同簇其它内容页 | ✅ `ArticleLayout` `others` 网格 |

> 在本站,「1 条→核心专题页」与「1 条→转化页」**合一**:工具支柱页既是簇的枢纽(hub)又是交易型落点。所以内容页顶部那张 CTA 卡同时满足这两项。

### 2.2 工具支柱页(`/cron` 等交易型)

| 内链槽位 | 数量 | 指向 | 现状 |
|---------|------|------|------|
| 面包屑 | 1 | 首页 › 本工具 | ✅ |
| "深入了解 X"模块 | 本簇全部 | 本簇内容页 | ⚠️ **硬编码**(见 §5) |
| "相关工具"模块 | 3 | 跨簇相关工具 | ❌ **取前 3 个,非语义**(见 §3) |
| 正文内语义内链 | 按需 | 相关工具 / 本簇内容页 | 视工具而定 |

### 2.3 首页 / 分类页 / Hub 页

- **首页**:权重最高,链向**全部工具支柱页** + 分类入口。是全站内链的总源头。
- **分类页** `/category/config`:链向该类下所有工具(给支柱页第二条入链)。
- **Hub 页** `/guides` `/compare` `/faq`:横向聚合**跨工具同类型**内容页,给深页第二条抓取路径(现未建,见 §6)。

## 3. 语义相关,而不是随机 —— 修掉 `slice(0,3)`

**这是当前最明确的一处反模式。** 现在工具支柱页的"相关工具"是这样取的:

```ts
// ToolPageLayout.astro / cron/index.astro —— 当前实现(有问题)
const related = tools.filter((t) => t.slug !== slug && t.status === 'live').slice(0, 3);
```

`slice(0,3)` 永远返回注册表里的**前三个工具**(cron / regex / nginx),与当前工具**毫无语义关系**。这直接违背通用方法论那句红线:

> 内链应根据**语义相关性**插入,而不是随机插入。

随机相关工具的害处:稀释主题信号(给 cron 页链一堆无关工具,反而模糊了它的主题)、浪费权重传递、用户点了没用。

### 决策:两级相关度来源

按优先级取相关工具,**同分类优先,跨分类靠人工关联补充**:

1. **人工关联(强)** —— 在 `tools.ts` 给每个工具加 `related?: string[]`,列出真正搭配使用的工具。这是"部署链路"这类**跨分类**关系唯一能表达的地方。例:
   - `cron` ↔ `docker-compose` ↔ `nginx`(自建部署/运维链路上常一起用)
   - `base64` ↔ `url-encode` ↔ `jwt`(编码/token 处理)
   - `color` ↔ `gradient` ↔ `contrast` ↔ `colorblind`(配色设计链路)
2. **同分类兜底(弱)** —— 人工关联不足 3 个时,用**同 `category`** 的其它 live 工具补齐。

```ts
// 建议实现:lib/related.ts
export function relatedTools(slug: string, n = 3): Tool[] {
  const self = getTool(slug)!;
  const manual = (self.related ?? []).map(getTool).filter((t): t is Tool => !!t && t.status === 'live');
  const sameCat = liveTools().filter((t) => t.slug !== slug && t.category === self.category && !manual.includes(t));
  return [...manual, ...sameCat].slice(0, n);
}
```

> `tools.ts` 是全站单一数据源(见其文件头注释),关联关系写在这里、由 `relatedTools()` 统一产出,支柱页与内容页共用,**杜绝各页各写**。

## 4. 正文内链与锚文本规范(《页面SEO.md》§4 预留项)

结构性内链(面包屑、CTA、推荐模块)由布局自动生成;**正文内的上下文内链**由作者在 Markdown 里手写(如 `cron/guide.md` 末尾的"继续学习"段与正文中的 `[Cron 表达式生成器](/cron)`)。这部分**需要规范 + 构建期校验**,否则容易劣化。

### 4.1 锚文本(anchor text)规则

锚文本是内链的"标签",直接告诉搜索引擎目标页讲什么。好的锚文本是**一句能读的描述**,差的是**指令或关键词堆**:

| ✅ 推荐(描述性、含主词) | ❌ 避免 |
|------------------------|--------|
| `Cron 表达式怎么写` | `点击这里` |
| `crontab 不执行怎么办` | `查看更多` / `详情` |
| `Nginx 反向代理配置生成器` | `SEO优化SEO优化SEO优化`(机械堆砌) |

五条原则(锚文本应做到):

1. **自然** —— 去掉链接后句子依然通顺,锚文本本身就是可读的词组,不是硬塞的指令。
2. **多样化** —— 同一目标页允许多种自然变体,**不要全站完全一致**。指向 `/cron` 可以是「Cron 表达式生成器」「在线生成 cron」「可视化 cron 工具」等,轮换使用。
3. **与目标页面相关** —— 锚文本 ≈ 目标页 H1/主词,读者一看就知道点进去是什么。
4. **不要全站完全一致** —— 清一色 exact-match 主词指向同一页 = 过度优化信号(见 §7)。
5. **不要机械堆砌关键词** —— 锚文本不是关键词农场,`SEO优化SEO优化` 这类重复堆词直接判低质。

补充落地约束:

- **落在语义相关的上下文里**:讲"写完要验证"时链到工具,讲"字段含义"时链到百科——**链在读者此刻真的想跳的地方**。
- **一屏不堆链**:同一目标页正文里**链一次即可**,不重复轰炸。
- **不自链**:页面不链自己(`ArticleLayout` 的 `others` 已 `filter(s => s.slug !== slug)`,正文里也别写)。

### 4.2 正文内链的标准落点(写作模板)

每篇内容页正文,建议在自然处埋这几类内链(对齐 §2.1 的"2–5 条"):

- **回链支柱页**(转化):讲到"动手做/验证"时 → `/{tool}`。
- **横链兄弟页**(补主题):讲到相邻子主题时 → 同簇的 `guide`/`examples`/`what-is-x`/`troubleshooting`。
- **末尾"继续学习"段**:2–4 条兄弟页链接(`cron/guide.md` 已是范例,推广到所有内容页)。

### 4.3 构建期校验(防劣化)

在构建流程加轻量断言(可放 `lib/` 校验或 Astro 集成钩子):

- **无死链**:正文所有站内链接指向真实存在的路由(工具 slug ∈ 注册表 / 文章 slug ∈ collection),否则构建报错。
- **无自链**:文章正文不出现指向自身 URL 的链接。
- **孤儿检测**:每个内容页至少被 1 个非面包屑入链引用(结构上已由推荐模块保证,校验兜底)。
- **锚文本黑名单**:命中「点这里 / 点击查看 / 这里 / 详情 / more」等无意义锚文本时告警。

## 5. 工具支柱页 = 完整主题导航中心(不是标签归档)

通用方法论强调:**专题页(pillar)不是简单的标签归档页,而是完整的主题导航中心**,应包含:主题介绍 / 核心教程入口 / 进阶教程入口 / 工具推荐 / FAQ / 最新文章 / 相关产品或服务 / 清晰的内部链接结构。

在 DevBox,**工具支柱页 `/cron` 本身就是这一簇的专题页**(URL 筒仓 `/cron/*` 的枢纽 + 交易型落点合一)。对照 checklist 盘点 `/cron` 现状:

| 专题页应含 | DevBox 支柱页对应 | 现状 |
|-----------|-----------------|------|
| 主题介绍 | 顶部"这是什么/什么时候用"导语卡 | ✅ |
| 核心教程入口 | "深入了解"→ `guide` / `what-is-cron` | ⚠️ 硬编码(见下) |
| 进阶教程入口 | "深入了解"→ `examples` / `troubleshooting` / `vs-*` | ⚠️ 同上,且未分「核心 / 进阶」层次 |
| 工具推荐 | "相关工具"模块 | ❌ `slice(0,3)` 非语义(见 §3) |
| FAQ | FAQ 折叠区(注入 `FAQPage`) | ✅ |
| 最新文章 | 该簇/博客最近更新 | ❌ 无(见下说明) |
| 相关产品或服务 | 工具本体即"产品"+ 相关工具 | ✅(工具本身)/ ⚠️(相关工具同 §3) |
| 清晰的内部链接结构 | 面包屑 + 深入了解 + 相关工具 + 正文链 | ⚠️ 部分,待 §3/§5 修 |

结论:本站的工具支柱页**已经具备"导航中心"的骨架**(有交互工具、导语、示例、FAQ、内容入口),不是空标签页;要补的是三处——**入口分层(核心/进阶)、相关工具语义化(§3)、入口自动生成(下)**。

### 5.1 入口分层:核心教程 vs 进阶

"深入了解"现在把 4 篇平铺。按 checklist,建议**分两组呈现**,给读者清晰路径:

- **先看(核心)**:`what-is-cron`(是什么)+ `guide`(怎么写)——入门主线。
- **深入(进阶)**:`examples`(示例大全)+ `troubleshooting`(排查)+ `vs-*`(对比)——按需查阅。

分组依据可直接用 frontmatter 的 `type`:`wiki`/`guide` 归"核心",`examples`/`troubleshooting`/`compare` 归"进阶"。

### 5.2 "最新文章"在本站的定位

通用模板的"最新文章"适合更新频繁的博客站。本站工具簇是**常青内容(evergreen)**、篇数固定,硬塞"最新"意义不大。落法:

- 工具簇内**不做**"最新文章"(内容稳定,分层入口已够)。
- 真正的"最新"归 `/blog`(泛信息型、持续产出),由首页/Hub 承载,不在工具支柱页重复。

### 5.3 入口自动生成:从硬编码改为读 collection

现在支柱页的"深入了解"是手抄的:

```astro
<!-- cron/index.astro 现状:硬编码 4 条 -->
{[
  { slug: 'what-is-cron', label: '是什么', title: 'Cron 是什么?格式详解' },
  { slug: 'guide', label: '使用教程', title: 'Cron 表达式怎么写' },
  ...
]}
```

问题:每个工具支柱页都要照抄一遍,**新增/改名文章要手动同步**,漏改就出死链或孤儿。而 `[slug].astro` 已经能从 content collection 拿到 `siblings`(见 `cron/[slug].astro` 的 `getStaticPaths`)——同一份数据应复用。

### 决策:抽 `getClusterArticles(tool)`,支柱页自动列出本簇文章

```ts
// lib/articles.ts 增补
import { getCollection } from 'astro:content';
export async function getClusterArticles(tool: string) {
  const all = await getCollection('articles', (e) => e.data.tool === tool);
  return all
    .map((e) => ({ slug: slugOf(e.id), title: e.data.title, type: e.data.type, order: e.data.order }))
    .sort((a, b) => a.order - b.order);
}
```

支柱页(以及 `ArticleLayout` 的兄弟页模块)都从这里取数据,`TYPE_LABEL` 统一给中文标签,**一处维护,全簇一致**,新增文章零改动自动出现在内链里。

## 6. Hub 页:给深页第二条抓取路径(排期项)

《网站结构.md》规划了 `/guides` `/compare` `/faq` 三个聚合 hub,横向把**跨工具的同类型内容**串起来(所有 `guide` 汇到 `/guides`,所有 `vs-*` 汇到 `/compare`)。当前未建。

内链价值:内容页现在只有"簇内纵向"入链(面包屑 + 支柱页 + 兄弟页);Hub 给它们加一条"**跨簇横向**"入链,缩短深页到首页的抓取距离、并形成类型级板块权威。canonical 仍归内容页自身,Hub 只**链接**不占有(见《网站结构.md》§3)。

排期:P0 内容页铺满后再建 hub(对齐《关键词矩阵.md》的批次顺序),届时 hub 页数据同样从 content collection 自动聚合,不手工维护列表。

## 7. 合规(Google Spam 政策)

参考 https://developers.google.com/search/docs/essentials/spam-policies

- **禁锚文本过度优化 / 关键词堆砌**:不要全站用同一串精确匹配主词做锚文本指向同一页(exact-match anchor 泛滥是垃圾链信号)。用自然变体。
- **内链为用户导航服务**,不是纯为传权重造链;每条内链在上下文里都应"有理由存在"。
- **不做隐藏链接 / 站内链接农场**:不堆一大片无关内链、不藏链接。
- **相关性真实**:相关工具/相关文章必须**真的相关**(这正是 §3 要修 `slice(0,3)` 的原因)。
