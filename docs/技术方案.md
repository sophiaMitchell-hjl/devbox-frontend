# DevBox 开发者工具箱 — 技术方案

> 版本 v1（第一阶段:纯静态 Astro,不上后端）
> 日期:2026-07-01

---

## 1. 产品定位

一个面向开发者/运维的**在线工具集站**。核心产品逻辑统一:**填参数 → 出配置/命令**,复制即用。

- 首页 = 工具卡片列表(带搜索/分类)
- 每个工具 = 一个独立 URL(`/cron`、`/regex`、`/nginx`…),独立 SEO,各自打长尾词
- 命名不绑死单个工具,后续加新工具不违和

**站名候选**(偏"开发者工具箱"感觉,不绑具体工具):

| 名字 | 备注 |
|------|------|
| **DevBox** / devbox.tools | 当前目录名,直观,`.tools` TLD 契合定位 |
| **Ctl** / ctl.tools | 短,运维味 |
| **Snippet Forge** | 偏"锻造配置"意象 |
| **配置匠 / confkit** | 中英双关 |

> 建议先用 **devbox** 作为项目内部代号,域名等验证期再定(见 §8)。域名不影响开发。

## 2. 架构决策(关键)

**第一阶段纯静态,不上 FastAPI。** 理由:

1. 首批工具(cron / regex / nginx / docker-compose)**全部是浏览器端纯计算**——字符串逻辑 + 模板填充,不需要服务器。
2. 纯静态站可直接部署到 Cloudflare Pages / Vercel,**零服务器成本、零运维**。
3. 静态页首屏即内容,对 SEO 最友好(不依赖接口渲染)。
4. 上线最快,适合冷启动验证需求。

**FastAPI 推迟到第二阶段引入**,触发条件(满足任一才做):
- 需要**保存/短链分享**配置(需存储)
- 需要**服务端真实校验**(如跑 `nginx -t`、`docker compose config`)
- 需要**用户账号 / 使用量统计**
- 需要 **AI 辅助生成**(把需求描述转成配置)

目录里预留 `api/` 位置和前端的 `lib/api.ts` 抽象层,到时无痛接入。

## 3. 技术栈

| 层 | 选型 | 理由 |
|----|------|------|
| 框架 | **Astro 5**(`output: 'static'`) | 内容站 + 工具页的最佳组合;默认零 JS,按需 island |
| 交互 | **Astro Islands + 原生 TS/JS**(必要时 Preact/Solid) | 每个工具的表单是独立 island,互不影响首屏 |
| 样式 | **Tailwind CSS**(`@astrojs/tailwind`) | 快;暗色模式;工具站 UI 统一 |
| 组件 | 轻量,自写为主 | 避免重依赖拖慢构建/SEO |
| 图标 | `astro-icon`(iconify) | 按需内联 SVG |
| 部署 | **Cloudflare Pages**(首选)或 Vercel | 免费额度足;全球 CDN;自定义域方便 |
| 包管理 | pnpm | 快、省盘 |

> 第二阶段后端:FastAPI + Uvicorn,独立部署(Fly.io / Railway / 自建 VPS),前端通过 `/api/*` 调用。

### 工具注册表(核心抽象)

`web/src/lib/tools.ts` 是单一数据源,首页列表、导航、sitemap、面包屑全从这里生成。加新工具 = 加一条记录 + 建一个页面:

```ts
export interface Tool {
  slug: string;          // 'cron'
  title: string;         // 'Cron 表达式生成器'
  desc: string;          // 一句话卖点(卡片+meta description)
  category: 'config' | 'cli' | 'text';
  keywords: string[];    // SEO 长尾词
  status: 'live' | 'soon';
  // 入门层(见《入门层与开发流程.md》):驱动小白导语与流程地图
  stage: string;         // 开发流程阶段,如 '⑤ 对外访问 + HTTPS'
  beginnerIntro: string; // 一句话:这是什么、干什么用(小白话)
  whenToUse: string;     // 什么时候会用到它(场景钩子)
  whyTool: string;       // 为什么用它而不是问 AI(即时/确定/可反向验证)
}

export const tools: Tool[] = [
  { slug: 'cron', title: 'Cron 表达式生成器与解释器', desc: '可视化生成 cron,人话解释,预览下次执行时间', category: 'config', keywords: ['cron 生成', 'crontab 每5分钟', 'cron 表达式解释'], status: 'live' },
  // ...
];
```

## 5. 首批工具的实现要点

按「实现成本低 + 长尾词好 + 高频自用」排序。首批做 **4 个**跑通流程。

### 5.1 `/cron` — Cron 表达式生成 + 解释(优先级最高)
- **输入**:两种模式 —— (a) 可视化选择器(分/时/日/月/周下拉+多选);(b) 直接粘表达式反向解析。
- **输出**:标准 5 段(可选 6 段含秒/Quartz)表达式 + **人话解释**("每天凌晨 3 点") + **未来 5 次执行时间**预览。
- **实现**:纯前端。表达式→人话可用 `cronstrue`;下次执行时间用 `cron-parser`(或 `croner`,一个库同时搞定解析+计算)。全部浏览器端,无网络。
- **SEO**:预置常见示例页锚点("cron every 5 minutes""cron every day at midnight"),这些是高流量长尾词。

### 5.2 `/regex` — 正则可视化调试
- **输入**:正则 + flags + 测试文本。
- **输出**:测试文本内**实时高亮匹配** + 分组(含命名组)列表 + 正则的**分段解释** + 常用模板(邮箱/URL/IP/手机号)。
- **实现**:必须前端(要实时)。匹配用浏览器原生 `RegExp`;高亮自己渲染;解释可先做"分 token 讲解",复杂可视化(铁路图)后置。**注意 ReDoS**:对用户正则加超时保护(用 `setTimeout`/Web Worker 跑,超时中断)。
- **SEO**:"正则 提取邮箱""javascript regex 分组"等。

### 5.3 `/nginx` — 反代/静态站配置生成(差异化优势,竞争小)
- **输入**:表单 —— 域名、上游地址、是否 HTTPS(含 Let's Encrypt 片段)、WebSocket 支持、gzip、缓存、客户端 body 大小、自定义 header。
- **输出**:完整可用的 `server {}` 块;可切 **Caddy** 等价配置(差异化)。
- **实现**:纯模板填充(`lib/nginx.ts` 里组合片段)。**第二阶段**可加"服务端 `nginx -t` 校验"。
- **SEO**:"nginx 反向代理配置""nginx websocket 配置""caddy 反代"。

### 5.4 第四个(二选一)
- **`/docker-compose`** — 常见服务模板(nginx/postgres/redis/自定义)拼 compose 文件,含 volume/network/环境变量/healthcheck。
- **`/curl`** — 把方法/URL/header/body/认证/表单填成 curl 命令,并可反向:curl → fetch/httpie。
> 建议按你自己碰得更多的选。默认 **docker-compose**(和 nginx 同属"配置生成"主题,SEO 聚合更强)。

### 通用交互约定
- 每个工具页统一:**左表单 / 右结果 + 复制按钮**,移动端上下堆叠。
- 结果区实时更新(输入即出结果,无"生成"按钮的等待感)。
- 所有计算在浏览器,**离线可用**(可选加 PWA)。
- **反向输入是一等能力**(对 AI 的护城河,见《入门层与开发流程.md》§6):不止单向"填表→生成",也支持"粘配置/表达式→解析+校验+可视化",用来验证 AI 的输出。

## 6. 页面与 SEO 方案

每个工具页由 `ToolLayout.astro` 统一产出,保证 SEO 结构一致:

1. **H1 = 工具全称**(含核心关键词),下面一段 80–120 字说明。
2. **工具交互区**(island)。
3. **"如何使用" + 常见示例**(静态内容,喂长尾词)。
4. **FAQ 区**(3–6 条),同时注入 `FAQPage` 结构化数据。
5. 相关工具互链(内链,提升整体权重)。

技术要点:
- `@astrojs/sitemap` 自动生成 sitemap;`robots.txt` 放行。
- 每页 `<title>` / `meta description` / `og:*` 由 `lib/seo.ts` 按工具注册表生成。
- 结构化数据:首页用 `WebSite`+`SearchAction`,工具页用 `SoftwareApplication` + `FAQPage`(JSON-LD)。
- 规范 URL(canonical)、语言标注。首批可只做中文,后续 i18n(Astro 原生支持)再扩英文页吃海外流量。
- 性能即 SEO:默认零 JS,island 按需水合,首屏 LCP 快。

## 6.5 内容架构:信息型关键词布局(Topic Cluster)

> 这是本站真正的流量引擎。工具页只吃「我要用工具」的**交易型词**;而「X 是什么 / X 怎么做 / X 报错怎么办」这类**信息型词**搜索量大得多、长尾极广,靠内容页承接。

### 关键词意图 → 页面类型映射

按 SEO 意图分层,每类词配对应页面类型(信息型是重点):

| 意图 | 关键词示例 | 页面类型 | 站内落点(以 cron 为例) |
|------|-----------|---------|------------------------|
| **信息型·是什么** | `cron 是什么`、`什么是反向代理` | 百科 / 概念 | `/cron/what-is-cron` |
| **信息型·怎么做** | `crontab 每5分钟怎么写`、`nginx websocket 配置` | 教程 / 示例集 | `/cron/guide`、`/cron/examples` |
| **信息型·排查** | `crontab 不执行怎么办`、`nginx 502 bad gateway` | 问题排查 | `/cron/troubleshooting` |
| 商业型·对比 | `cron vs systemd timer`、`nginx vs caddy` | 对比评测 | `/cron/vs-systemd-timer` |
| **交易型·工具** | `cron 在线生成`、`正则测试` | **工具(支柱页)** | `/cron` |

### Topic Cluster 结构

每个工具是一个**主题集群**:工具页 = 支柱页(pillar),外围一圈信息型内容页(cluster),双向内链。

```
        ┌─────────────────────────────────────┐
        │  /cron  (支柱页 = 工具本体 + 简介)      │  ← 交易型词
        └───▲───────▲────────▲────────▲────────┘
            │       │        │        │   (内容页 CTA 导流进工具;工具页反链撑内容)
   ┌────────┴─┐ ┌───┴────┐ ┌─┴──────┐ ┌┴─────────────┐
   │ what-is  │ │ guide  │ │examples│ │troubleshooting│  ← 信息型词
   │ (百科)   │ │(教程)  │ │(示例集)│ │  (排查)       │
   └──────────┘ └────────┘ └────────┘ └──────────────┘
```

**转化闭环**:信息型内容页排名 → 拉进学习/排查流量 → 页内 CTA 卡片「用在线工具直接生成 →」导入支柱工具页 → 用户完成任务。既吃流量又提转化。

### URL 与实现

- **URL**:内容页嵌在工具路径下,集群更紧凑、面包屑天然:`/cron`、`/cron/what-is-cron`、`/cron/guide`、`/cron/examples`、`/cron/troubleshooting`。
- **Slug 用英文/短横线**(`what-is-cron`),标题/H1/正文用中文——URL 干净、可读、可分享;中文 SEO 靠正文和 H1,不靠 URL。
- **内容用 Astro Content Collections**:`src/content/articles/*.md`,frontmatter 带 `tool`(归属哪个工具)、`type`(wiki/guide/examples/troubleshooting)、`title`、`description`、`keywords`。工具注册表 + 内容集合共同驱动集群页、内链、sitemap。
- **内链自动化**:`ToolLayout` 底部自动列出「本工具的相关文章」;每篇文章顶部/中部自动插入「→ 打开 XX 在线工具」CTA;文章之间按 `tool` 互链。全部从数据生成,不手工维护。

### 每篇信息型内容的写作骨架(SEO 模板)

1. **H1 = 目标关键词的自然问法**(「Cron 表达式是什么?一文讲清 5 个字段」)。
2. 开头 40–60 字**直接回答**(抢精选摘要 / featured snippet)。
3. 正文分 H2/H3,覆盖同簇长尾(「每分钟」「每5分钟」「每天几点」各一个 H2)。
4. 关键处嵌**工具 CTA 卡片**。
5. 结尾 **FAQ 区**(注入 `FAQPage` JSON-LD),覆盖「People Also Ask」问题。
6. 文章类型对应结构化数据:教程用 `HowTo`,百科用 `Article`,FAQ 用 `FAQPage`。

### `/cron` 集群首批文章清单(样例)

| 文件 | 类型 | 主打词 |
|------|------|--------|
| `what-is-cron.md` | 百科 | cron 是什么、crontab 格式说明 |
| `cron-guide.md` | 教程 | cron 表达式怎么写、5 个字段含义 |
| `cron-examples.md` | 示例集 | 每5分钟 / 每天凌晨 / 每周一 …(一个 H2 一个高频长尾) |
| `crontab-not-running.md` | 排查 | crontab 不执行 / 不生效 怎么办 |

> 每个工具照此各配 3–4 篇,首批 4 工具 ≈ 12–16 篇内容页 + 4 个工具页,构成完整集群。

## 7. 部署与 CI

- **Cloudflare Pages**:连 GitHub 仓库,`web/` 为根,`pnpm build` 出 `dist/`,推送即部署。免费、全球 CDN、自定义域 + 自动 HTTPS。
- 分支预览:PR 自动生成预览 URL,方便验证。
- 分析:用 Cloudflare Web Analytics 或 Plausible(隐私友好、无 cookie 弹窗),看哪些工具真有人用 → 指导后续优先级。

## 8. 路线图

**Phase 0 — 脚手架(0.5 天)**
Astro + Tailwind 初始化;BaseLayout/ToolLayout;工具注册表;首页列表;部署跑通(空工具页也先上线拿到域名+索引)。

**Phase 1 — 首批工具集群(核心)**
每个工具做成一个完整 **Topic Cluster**:工具页(支柱)+ 3–4 篇信息型内容(百科/教程/示例/排查),含内链与工具 CTA。顺序 `/cron` → `/regex` → `/nginx` → `/docker-compose`。
> 单个工具先做「支柱工具页」跑通,再补内容页——但内容页才是流量大头,不能省。首批 ≈ 4 工具页 + 12–16 内容页。

**Phase 2 — 内容纵深与验证**
接分析看数据:哪些信息型词进来了、哪些工具在用。补长尾示例页 / 排查页(信息型词几乎无上限);按热度加第 5–8 个工具(clash/mihomo 规则、caddy、systemd unit、ffmpeg、git 命令…),每个同样配套内容集群。

**Phase 3 — 引入 FastAPI(按需)**
出现 §2 触发条件时再上:短链分享、服务端校验、AI 辅助生成。前端 `lib/api.ts` 已抽象,接入无痛。
