# DevBox 入门层:面向小白 + 开发流程串联

> 工具箱不只服务"会用的人查语法",也要让小白看懂:每个工具**是什么、在开发/部署的哪一步、为什么需要它**。降低门槛 = 扩大受众 + 承接海量入门信息型词。
> 日期:2026-07-01

---

## 1. 核心原则:渐进式披露(别做成两个站)

**同一个工具页同时服务两类人**,靠分层排布,互不干扰:

```
┌───────────────────────────────────────────────┐
│ ① 小白导语(1–2 句):这是什么 · 什么时候用      │ ← 新手看懂
├───────────────────────────────────────────────┤
│ ② 工具本体(表单 → 结果 → 复制)                │ ← 老手直接用,不被科普挡住
├───────────────────────────────────────────────┤
│ ③ 深入:使用教程 / 示例 / 是什么 / 排查(链接)  │ ← 想学的人往下走
└───────────────────────────────────────────────┘
```

原则:**工具永远在首屏显眼位置,科普不喧宾夺主**;小白靠导语和"深入"入口延展,老手一眼看到工具直接用。

## 2. 开发流程地图(把工具串起来)

给小白一张"开发/部署全流程"地图,标出每个工具落在哪一步、干什么用。作为独立页 `/guide/dev-workflow`,并在首页放精简版。

| 阶段 | 在做什么(小白话) | 相关工具 | 工具的作用 |
|------|------------------|---------|-----------|
| ① 本地开发 | 在自己电脑上写代码、调试 | — | — |
| ② 处理文本/数据 | 校验邮箱、提取内容、清洗字符串 | **正则** | 用规则匹配/提取文本,不用写一堆 if |
| ③ 定义与打包服务 | 把应用和数据库等"打包"成能一键启动的服务 | **Docker Compose** | 一个文件描述多个服务,一条命令全起来 |
| ④ 部署到服务器 | 把服务搬到一台 24h 在线的服务器上 | (主线指南) | 见 §3 |
| ⑤ 对外访问 + HTTPS | 让别人能用域名访问,并加上小绿锁 | **Nginx / Caddy** | 反向代理:把域名请求转给你的服务,顺带配 HTTPS |
| ⑥ 定时与运维 | 每天自动备份、定时跑任务 | **Cron** | 定时触发命令,无需人工盯着 |

> 这张表也回答了"这些工具作用于开发哪个步骤、有什么作用"——每个工具页顶部的小白导语,就是从这张表里取自己那一行。

## 3. 主线支柱指南:《从零把网站部署到服务器》

一篇串联全流程的入门支柱(`/guide/deploy-to-server`),小白照着走一遍就能上线一个网站;每一步 CTA 导进对应工具。这是**顶级流量入口**(搜索量极大)+ 把工具串成实用路径。

大纲(每步 = 一个 H2,含"是什么 + 为什么 + 怎么做 + 用哪个工具"):

```
h1  从零把网站部署到服务器(新手完整指南)
h2  第 1 步:准备一台服务器(VPS 是什么、怎么选)
h2  第 2 步:连上服务器(SSH 是什么、怎么登录)
h2  第 3 步:装运行环境(Docker 是什么、为什么用它)
h2  第 4 步:定义你的服务(用 docker-compose 编排)   → CTA: /docker-compose
h2  第 5 步:让外网能访问(反向代理是什么)           → CTA: /nginx
h2  第 6 步:加上 HTTPS(证书是什么、怎么配)          → CTA: /nginx(Caddy 自动证书)
h2  第 7 步:自动化运维(定时备份/任务用 cron)        → CTA: /cron
h2  常见问题(部署失败、访问不了、502…)
```

每步末尾一句"想深入看 → {对应工具的教程/百科}",形成 主线指南 ↔ 工具 ↔ 工具百科 的三层内链。

## 4. 每个工具页的"小白视角"模块

工具注册表新增三个字段,驱动导语与卡片(见《技术方案》§4 工具注册表):

```ts
interface Tool {
  // …原有字段…
  stage: string;          // 开发流程阶段,如 '⑤ 对外访问 + HTTPS'
  beginnerIntro: string;  // 一句话:这是什么、干什么用(小白话,无术语)
  whenToUse: string;      // 什么时候你会用到它(场景钩子)
}
```

示例(Nginx):
- `stage`: `⑤ 对外访问 + HTTPS`
- `beginnerIntro`: 反向代理:把用户对你域名的访问,转发给后台真正跑的程序,顺便管好 HTTPS。
- `whenToUse`: 当你的应用跑在服务器某个端口上,想用域名 + 小绿锁对外提供访问时。

呈现位置:
- **工具卡片**(首页/分类页):副标题显示 `beginnerIntro`,让小白扫一眼就懂这工具干嘛。
- **工具页顶部导语**:`beginnerIntro` + `whenToUse` + "属于开发流程第 ⑤ 步"小徽标(链到流程地图)。

## 6. 为什么用它,而不是直接问 AI(核心定位)

AI 时代小白第一反应是问 ChatGPT。工具要赢,必须在特定维度**比 AI 更方便、更可信**。诚实讲:开放式/新颖问题 AI 更强;但"**填参数 → 出配置/命令**"这类**确定性转换**,专用工具全面胜出。这句话要直接讲给小白听。

| 维度 | 直接问 AI | DevBox 工具 |
|------|----------|------------|
| **速度** | 等它生成一段话 | 输入即出结果,零等待 |
| **正确性** | 可能幻觉、编出不存在的参数 | 用真实解析库(croner / 原生 RegExp),结果确定、可验证 |
| **交互** | 一问一答,改需求要重新描述 | 改一个字段实时更新(正则高亮、cron 下次执行预览) |
| **表达成本** | 要写清 prompt 才给对 | 勾选项即可,无需组织语言描述 |
| **可复现** | 每次回答可能不同、可能过时 | 同输入同输出,稳定不变 |
| **隐私** | 配置/数据发给第三方 | 纯浏览器计算,不出本机,内网可用 |
| **成本** | 消耗 token / 有次数限制 | 免费无限次、免登录 |
| **学习** | 给答案不一定解释 | 边生成边"人话解释" + 可视化 + 执行预览 |

### 定位:做 AI 的"校验器 + 可视化层",不做对手

AI 生成的 cron / 正则 / nginx 配置**经常有错或过时**。让用户把 AI 的输出**粘进工具,一键验证是否正确、可视化看效果**:

- 话术:**"AI 生成,DevBox 验证。"** 把 AI 从竞争对手变成上游——用户问完 AI 来这儿核对。
- 因此每个工具都做**反向输入**(不只生成,也能解析+校验+可视化):
  - **cron**:粘表达式 → 人话解释 + 未来执行时间(验证 AI 给的对不对)
  - **regex**:粘正则 → 实时高亮 + 分组(验证 AI 的正则匹配对不对)
  - **docker-compose / nginx**:粘配置 → 校验语法 + 格式化 + 高亮问题
- 反向输入是**接住 AI 用户**的关键功能,列为每个工具的一等能力。

### 为什么这是护城河(SEO 防御)

AI 搜索(Google SGE / ChatGPT)正在吃掉**纯信息型文章**的流量——答案直接显示在聊天框里,用户不再点进网页。但**交互工具无法被一段文字答案替代**:你没法在聊天框里实时拖 cron 字段、高亮正则匹配。所以:

- **工具本体是护城河**,信息型内容是流量入口(内容可能被 AI 摘走,但会把要"动手做"的用户导进工具)。
- 越是需要**实时交互 / 确定结果 / 反复调参**的工具,越抗 AI 替代 → 优先做这类。

### 落到产品

- 工具注册表加一字段 `whyTool`,工具页导语放一句"**为什么用它,而不是问 AI**":

```ts
interface Tool {
  // …
  whyTool: string; // 如:'AI 可能编错 cron,这里用真实库解析,填即得、可反向验证 AI 的输出'
}
```
- **首页**放一句总定位:"AI 会幻觉、要描述、每次不同;这里填参数即得**确定结果**,还能**反向验证 AI 的输出**。"
- 每个工具**必做反向输入/校验**,不止单向生成。

## 8. 分寸把握

- 科普**服务于工具**,不是写教程站——每篇入门内容都要导回某个工具或让用户完成某件事。
- 老手体验优先级不降:工具永远在首屏,导语简短可折叠。
- 入门词虽大,但按《关键词矩阵》批次(先低竞争长尾)推进,不一上来硬冲"网站部署"这类大词。
